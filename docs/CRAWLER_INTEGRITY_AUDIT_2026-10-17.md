## 高优先级的覆盖与数据丢失风险

### A. P1：不完整谱面内容会覆盖已有完整记录

`crawlers/stb.py` 的 `parse_chart_page` 为缺失内容填空字符串、0 或 None；`save_chart_data` 仅要求 SID 非空，就整体替换 `songs` 和 `charts`。

隔离复现：先保存真实 CID 17302，再模拟只剩 `Back to song` 链接的部分 HTML。第二次仍返回保存成功，原谱师 UID、版本、更新时间变为 None/空，状态变成 Alpha=0，热度归零，歌曲标题、艺术家变空，BPM/长度归零。当前只对封面、打赏、游玩数和新增不推荐数做了部分保留保护。

**修正方向：** 解析结果需要记录字段是否实际出现、页面是否完整；必需结构缺失时拒绝入库。更新使用明确的字段级规则，区分缺失、显式清空和真实 0。

### B. P1：不完整玩家资料会清空头衔、成就和已知字段

`parse_player_profile_full` 只要有名字就可返回“成功”；`save_player_profile` 随后整体替换基础资料，并删除再插入全部头衔、成就。

基于真实玩家页的隔离复现：截掉资料、成就、头衔区但保留名字，仍保存成功；原注册日期、Gold 等变 None，头衔和成就归零。不能把抓取时缺失区域等同于用户删除资料或失去成就。

### C. P1：玩家资料保存失败后，部分修改仍会提交

`save_player_profile` 的异常处理先写错误状态并 `commit()`，之后才 `rollback()`，导致此前同一事务的业务修改一起提交。

故障注入复现：在成就写入时触发数据库错误。函数返回 None，但前面已更新的 Gold 和已删除的头衔仍落库，后续 rollback 无法撤销。

**修正方向：** 业务事务首先完整回滚，再用独立事务记录失败状态。

### D. P1：保存失败仍被标成成功，进一步污染完成进度

`crawl_player_profile` 未检查 `save_player_profile` 的返回值；资料保存返回 None 时，仍可能加入 `processed_uids` 并返回 True。范围采集消费者据此把 UID 标为全局完成。排名为空或某模式失败，也没有完整性要求。

隔离复现已确认返回 True 且 UID 进入已处理集合。全局完成位图没有到期机制，同一范围后续运行会跳过它；这会把一次保存失败变成持续漏采。

### E. P1：旧数据和不同实体的时间会覆盖较新数据

谱面保存没有检查源更新时间：较早的响应仍可覆盖较新业务值。歌曲的 `last_updated` 又直接使用当前处理的**谱面**时间，而非歌曲更新时间。先保存新谱面，再保存同歌旧谱面，就能使歌曲时间倒退。

隔离复现已验证：2010 年的谱面时间能覆盖较新的记录并写入歌曲时间。库内还有 6,158 首歌曲的 `last_updated` 早于至少一个关联谱面；该统计只是异常筛查，不能逐条作为错误判据。SID 4448 的页面与本地时间差异是实际样本。

### F. P1：评论抓取失败/分页截断后全量替换

首轮报告中的问题仍未修复：异常、业务失败、正常空集和截断结果缺少区分；保存时删除已有评论后仅插入本次结果。当前不推荐功能已经区分投票方向，但没有改变这套全量替换策略。

**修正方向：** 部分成功结果只能增量合并，只有明确完成的快照才可删除缺席项；分页完整性与统计完整性需单独存储。

## 重复采集、漏采与恢复逻辑

### G. P1：玩家批处理入口缺少被调用的方法，范围入口也不能正常结束

- `PlayerProfileCrawler` 没有实现 `crawl_players_batch`，但单 UID、UID 列表、文件、数据库和排行榜入口都调用它，会触发 AttributeError。
- 范围采集的 producer 引用模块中未初始化的 `stop_requested`，通常会在入队前失败。
- 消费者取到结束哨兵 None 时直接退出，没有 `task_done()`；主线程 `task_queue.join()` 会等待未完成的哨兵任务。

隔离检查确认方法缺失；在临时补入 stop 标志以测试后续路径后，一名玩家的队列最终为空，却仍有 `unfinished_tasks=1`，原 join 将一直等待。复现脚本拦截等待，没有遗留挂起进程。

### H. P1：一张谱面成功就可能跳过整首歌

任一谱面保存成功就把 SID 加入 `processed_songs`；SID 顺序采集、倒序采集、主页来源又把该集合解释成“整首歌全部完成”。同一实例先抓到该歌曲的一张谱面后，其他入口可能直接跳过其余谱面。

SID 重试还有独立缺陷：遇到第一张成功的谱面就 break，并把整个 SID 从失败列表移除。三张谱面的隔离样本只请求第一张，失败标记已经清除。

**修正方向：** 分开记录歌曲发现完成、CID 列表获取完成和每个 CID 的采集状态；只有明确处理完当前完整 CID 集合才能标整首歌完成。

### I. P1：临时歌曲请求失败被永久记录为“空歌曲”

`get_charts_from_song_page` 对 404、网络错误、解析失败都返回 `[]`。SID 扫描默认把它加入 `empty_songs`，后续恢复会跳过。

隔离复现：模拟 HTTP 503，SID 4448 被写入 `empty_songs`。生产进度文件已有 13,124 个 empty_songs；没有逐个复核，因此不能声称全部误判。

### J. P1：停止和收尾阶段可能丢失或复活重试任务

- `process_retry_queue` 先复制再清空原队列，中途停止时剩余本地任务没有放回。隔离复现中，两项待重试任务在停止后全部消失。
- CID 扫描在 finally 中保存进度，然后才执行最终重试；重试结果没有再次保存。隔离复现中内存队列已清空，磁盘进度仍保留已成功的任务，下一次会再次抓取。
- JSON 进度文件是直接覆盖写入，缺少原子替换；异常退出可能造成截断，加载失败后又回到默认起点。这一项由源码确认，未破坏实际进度文件测试。

### K. P2：新版来源反复从第一页开始，限额可能使后段长期得不到处理

`crawl_from_new_api` 每次将 `from_offset` 置 0；跨进程不保存已处理 CID 或继续位置。用真实 SID 4448 的 219 个 CID 列表和每轮 2 张的隔离限额重放，两轮都抓到相同的 `[130279,130278]`，其余 CID 没有继续机会。

现有多来源统计还将“此前已处理而跳过”的 CID 计为成功。实际日志中总来源成功数为 120，但写入分类统计只有 70。这不等于重复写了 120 行，而是成功数不能代表唯一采集数或完成度。

**修正方向：** 建立持久待处理队列，区分新增、刷新、已跳过、失败及唯一 CID；限额应留下可继续的游标及未完成歌曲。

### L. P2：来源精度差异制造虚假变化，并把等级写成 0

真实玩家 100704：API 准确率为 `99.4562586079749`，HTML 为 `99.46`；个人页排名解析固定给 `lv=0`。保存函数按浮点数精确比较，等级保护又仅在其他核心字段完全相同时生效。

隔离复现只切换来源精度、保持其他数值相同，四次保存得到四条变化记录，等级依次 `74,0,74,0`。这会夸大历史变化并覆盖最新已知等级。已有防 0 回归测试仅覆盖“其余字段完全相同”的情况。

### M. P2：更新队列没有覆盖全部已知玩家，调度时间未被使用

`crawl_from_database` 只查询 `player_profile_crawl_status`，不合并 `player_profiles` 和 `player_identity` 中没有状态行的 UID。实测 1,105,336 份已有资料不在该状态表，另有 1,311 个身份 UID 也无状态行。

代码保存 `next_crawl_time`，但取任务时不按该时间过滤；失败时设置未来重试时间，`needs_update=1` 却会使它立即再次入选。范围完成位图也不会因资料过期自动清除。

## 已补齐 Not recommend

真实 CID 4236 的 talk 接口返回 `type=1` 且正文为 `Not recommended, score: ...`，官方详情同时返回 `like=45,dislike=4`。因此 `type=1` 不是正向推荐的充分条件。

已实现并写入当前项目及本地数据库：

- `charts.not_recommend_count`：来自官方 `dislike`，缺失为 NULL；不会用截断的历史事件数推算当前总数，未知值也不覆盖已有计数，显式 0 正常保存。
- `chart_comments.is_not_recommend`：按去除 HTML 后的明确投票前缀识别；负向投票不再标成正向推荐，也不计入新采集的普通评论数。方向未知的 type=1 不猜成正向。
- 新版 API 和旧页详情采集都能补充官方不推荐总数；评论 API 返回方向标记，排除投票时也排除负向投票。
- 旧库自动增列兼容；新增 `scripts/backfill_not_recommend.py`，支持预览、备份和历史分类回填。

实际回填：**4,387 条明确负向投票 + 116 条旧解析漏识别的正向投票，共修正 4,503 条方向标记**。最初文本检索命中 4,388 条，其中 1 条只在普通评论正文提及，不按负向投票回填。没有删除或新增历史评论。

抽样官方总数已入库：CID 17302 → 381；8438 → 0；4241 → 1；4236 → 4。其他谱面保持 NULL，随后续采集补齐。旧推荐/评论汇总因来源口径混用，不能直接减去历史负向事件数；本轮没有这样盲目修改汇总。

修改前备份位于 `logs/not_recommend_backups/`。Token 更新及这项用户明确要求的补齐，是本轮对生产文件/数据的写入；其余审计发现仍只是报告和隔离验证。

## 数据类型及字段覆盖缺口

| 数据类型或字段 | 当前覆盖 | 处理建议 |
| --- | --- | --- |
| 当前正/负投票总数与投票事件 | 负向总数和标记本轮已新增；旧正向总数仍混有事件口径 | 汇总采用明确来源，事件保留独立标记和完整性 |
| 谱面 `checksum` | 实际 API 有值，未入库 | 若要识别内容改版，应保存，不只比较标题和时间 |
| 歌曲 `titleOrg/artistOrg` | 实际 API 有值，现有表只有一套标题/艺术家 | 分列存储原文与其他显示名，避免两种来源来回覆盖 |
| 标签 | 实际 HTML 有 Tags，未入库 | 是否纳入采集范围需明确；当前不能视为已覆盖 |
| 真实歌曲更新时间 | 页面有值；现用谱面时间替代 | 独立抓取并保存歌曲元数据 |
| 缺失/真实 0/解析失败/字段未公开 | 大部分字段无法区分 | 需要字段状态及校验，不再统一默认 0/空 |
| 来源、源时间、采集完整性、分页游标 | 谱面/歌曲缺少逐条来源和完整性记录；EXP 保存的 source 参数未落库 | 需要可追溯元数据，否则难以判断哪个值有权覆盖 |
| 谱面、歌曲、资料历史快照 | 主要表只保留最新值，覆盖后不能还原历史内容 | 若目标包含热度、投票、审核状态等历史分析，需要快照或变更表 |
| 成就/头衔获得时间 | 页面未核实到真实获得日期；重建关联记录会重置默认时间或清空已有日期 | 首次观察时间和真实获得时间应区分，不能用当前采集时间冒充 |

这些覆盖缺口中，有些属于能力范围尚未实现，不全部等同于解析 bug。

## 验证与修复顺序

本轮真实响应位于 `logs/crawler_audit_20261017/authenticated/`。18 项完整度观察由 `integrity_reproduce.py` 在内存数据库、临时进度文件和模拟失败下复现；没有改动生产进度文件，没有留下挂起线程或批量采集任务。真实页面的字段映射和覆盖逻辑分别验证，故障注入不冒充线上故障。

Not recommend、计数字段、谱面服务及排行榜相关单元测试共 30 项通过；完整 HTTP 路由测试仍受当前环境缺少 `httpx2` 限制，未声称全套通过。

优先顺序建议：修复玩家采集入口与完成标记 → 事务回滚与部分记录保护 → 评论完整性与 SID/CID 任务状态 → 登录/删除误判 → 持久队列、来源精度及覆盖范围 → 数据类型补齐与历史回采。原报告中的 UID 错配、页面 SID 和排名误解析也仍需修复。
